```markdown

## 1.1. Бюджетирование проектов, финансовые отчёты и прогнозы

**Подходящий тип СУБД:** реляционная (табличная) - рostgreSQL, Oracle.

В этой задаче важны строгие связи между данными, целостность (запрет «неправильных» сумм) и сложные аналитические запросы. Реляционные СУБД гарантируют транзакции, поддерживают JOIN и отчёты.

### 1.1.* Хеширование выполняется медленно. Какое API использовать для ускорения?

Для ускорения можно использовать:
- аппаратное ускорение через Intel QAT или AMD CCP;
- OpenSSL engine с оффлоудом хеширования;
- оптимизации с помощью SIMD (например, AVX-512);
- либо перейти на более быстрый алгоритм хеширования (например, с bcrypt на scrypt с подходящими параметрами).

---

## 1.2. Лендинги и CRM (лиды, маркетинг, продажи)

**Типы СУБД:**

| Система | Тип СУБД | Почему |
|---------|----------|--------|
| Лендинги | Документоориентированная (MongoDB) | Быстрая запись, гибкая схема, легко менять структуру лидов |
| CRM | Реляционная (PostgreSQL) или документоориентированная | Нужны связи «клиент → сделка → менеджер» и аналитика |

### 1.2.* Можно ли решить задачу одной СУБД? Если да, то какой и с какой реализацией?

**Да, можно.**  

**СУБД:** PostgreSQL.  
**Реализация:** использовать тип данных `JSONB`.  

Это позволяет:
- хранить документы гибко (как в MongoDB);
- делать индексы и транзакции;
- выполнять сложные аналитические запросы для маркетинга и продаж.

---

## 1.3. База знаний (нормы, правила, обучающие материалы)

**Подходящий тип СУБД:** документоориентированная или иерархическая.  
**Пример:** MongoDB или даже встроенная вики-система. Но если строго в рамках СУБД — документная.

**Почему:**  
Данные имеют чёткую структуру (разделы, подразделы), не требуется сложных финансовых операций. Важен быстрый поиск по тексту.

### 1.3.* Можно ли использовать существующую СУБД из задач выше?

**Да.**  

Например, если  уже выбрали PostgreSQL с `JSONB` для п. 1.2, то можно:
- создать отдельную схему (schema) внутри той же БД;
- хранить статьи как JSON-документы (заголовок, раздел, текст, автор, дата);
- использовать полнотекстовый поиск PostgreSQL (GIN-индексы).

Это проще, чем разворачивать отдельную БД.

---

## 1.4. Логистика (маршруты, курьеры, доставка)

**Подходящий тип СУБД:** реляционная с графовыми расширениями или отдельная графовая СУБД.  
PostgreSQL + pgRouting, Neo4j.

«Быстро работать со связями» — это про графовые алгоритмы: поиск кратчайшего пути, оптимизация маршрутов. Обычные JOIN-ы на больших данных становятся медленными.

### 1.4.* Можно ли подключить отдел закупок или для них лучше сделать отдельную СУБД в связке?

**Лучше сделать отдельную СУБД** (например, реляционную для закупок: поставщики, материалы, цены, заказы), а с БД логистов связать её **через API или обмен данными**.

- у логистов — графовые запросы;
- у закупок — строгие таблицы, согласования, документы.

Смешивать их в одной БД —  усложнит архитектуру и получить потерю производительности. А связь через обмен данными (логисты запрашивают, у какого поставщика быстрее получить материал) будет гибкой.

## 1.5.* Можно ли все перечисленные задачи решить одной СУБД? Если да, то какой?

**Да, можно.**  

**СУБД:** PostgreSQL.

**Как закрываются задачи:**

| Задача | Как решает PostgreSQL |
|--------|----------------------|
| Бюджетирование | Обычные таблицы, транзакции, целостность |
| Лендинги / CRM | Тип JSONB (NoSQL внутри реляционной БД) |
| База знаний | JSONB + полнотекстовый поиск |
| Логистика | Расширение pgRouting (графовые алгоритмы) |
| Отчёты и аналитика | Оконные функции, материализованные представления |


Такая монолитная БД сложнее в администрировании (нагрузка, индексы, кэш).  
На старте проекта — отличное решение. При росте нагрузок логистику и лендинги можно вынести в отдельные БД. Но в рамках учебного и реального небольшого проекта PostgreSQL справляется полностью.
```

### Задание 2. Транзакции

2.1. Пользователь пополняет баланс счёта телефона, распишите пошагово, какие действия должны произойти для того, чтобы 
транзакция завершилась успешно. Ориентируйтесь на шесть действий.

2.1.* Какие действия должны произойти, если пополнение счёта телефона происходило бы через автоплатёж?

*Приведите ответ в свободной форме.*

---

```markdown
### 2.1. Пользователь пополняет баланс счёта телефона (6 шагов)

Чтобы транзакция прошла успешно, должны быть выполнены такие действия:

1. **Начало транзакции** – система фиксирует, что сейчас будет выполняться группа операций, которые либо выполнятся все вместе, либо не выполнится ни одна.

2. **Проверка источника средств** – например, списание с банковской карты или с внутреннего счёта. Система убеждается, что денег достаточно.

3. **Списание средств** – сумма блокируется или списывается со счёта плательщика.

4. **Зачисление на счёт телефона** – указанная сумма прибавляется к балансу телефона.

5. **Фиксация операции** – создаётся запись (лог) о том, что пополнение произошло (дата, время, сумма, кто пополнил).

6. **Подтверждение транзакции (COMMIT)** – система «замораживает» все изменения. Если на любом из предыдущих шагов произошла ошибка, транзакция откатывается (ROLLBACK), и деньги не списываются.

> **Суть**: либо деньги списались И зачислены (всё хорошо), либо ничего не произошло (откат).

---

### 2.1.* Пополнение через автоплатёж

При автоплатеже шаги почти те же, но добавляются условия:

1. Система в фоне проверяет баланс телефона (например, раз в день).
2. Если баланс ниже порога (например, < 50 ₽) – инициируется транзакция.
3. Автоматическое списание с привязанной карты/счёта без участия пользователя.
4. Зачисление на счёт телефона.
5. Логирование с пометкой «автоплатёж».
6. COMMIT.

Автоплатёж не должен повторяться многократно при ошибке. Если денег на карте не хватило – транзакция откатывается, и повторная попытка делается, например, через день.

```

## Задание 3. SQL vs NoSQL

3.1. Напишите пять преимуществ SQL-систем по отношению к NoSQL. 

3.1.* Какие, на ваш взгляд, преимущества у NewSQL систем перед SQL и NoSQL.

*Приведите ответ в свободной форме.*

---
```markdown
### 3.1. Пять преимуществ SQL-систем перед NoSQL

1. **Чёткая структура (схема)** – вы заранее знаете, какие поля в таблицах и какого они типа. Это дисциплинирует данные.

2. **Гарантия целостности** – можно настроить внешние ключи (foreign keys), чтобы не было «висящих» записей.

3. **Сложные запросы через JOIN** – легко соединять данные из 2–3–5 таблиц в одном запросе.

4. **Транзакции ACID** – атомарность, согласованность, изоляция, долговечность. Для финансовых и критичных операций это обязательно.

5. **Стандартизация** – язык SQL (почти) один и тот же в разных СУБД (MySQL, PostgreSQL, Oracle). Проще мигрировать и находить специалистов.

---

**NewSQL** – это как классические SQL-системы, но «прокачанные» под масштабирование (как NoSQL).

**Преимущества:**
- **Горизонтальное масштабирование** (как в NoSQL) – можно разложить данные на сотни машин.
- **При этом полная поддержка SQL и ACID** – как в традиционных SQL.
- **Высокая производительность** для OLTP-нагрузок (много мелких транзакций) – лучше классических SQL.
- **Нет необходимости «рулить» шардирование вручную** – система делает сама (в отличие от обычного SQL).
- **Совмещает гибкость NoSQL со строгостью SQL** – можно начать с гибкой схемы, а потом зафиксировать.

**Примеры:** Google Spanner, CockroachDB, TiDB.

SQL – надёжен + сложные запросы, но плохо масштабируется.  
NoSQL – хорошо масштабируется, но слабая целостность и сложные запросы.  
NewSQL – надёжность + сложные запросы + масштабирование.
```

## Задание 4. Кластеры

Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу 
выделено 1000 машин. 

На основе какого критерия будете выбирать тип СУБД и какая модель *распределённых вычислений* 
здесь справится лучше всего и почему?

*Приведите ответ в свободной форме.*

---
```markdown
### По какому критерию выбирать тип СУБД?

Главный критерий – **модель распределённых вычислений** и **согласованность данных**.

Если важна **точность результатов** (например, финансовая аналитика, агрегация логов) – нужна **строгая согласованность**.  
Если допустима небольшая задержка в обмен на скорость – можно **согласованность в конечном счёте (eventual consistency)**.

### Какая модель распределённых вычислений справится лучше?

Для **1000 машин и большого объёма вычислений** лучше всего подойдёт:

**MapReduce (или его современный аналог – Spark)**

**Почему:**
- Данные разбиваются на части и распределяются по 1000 машинам (Map-фаза).
- Каждая машина считает свой кусок независимо.
- Потом результаты собираются и объединяются (Reduce-фаза).

**Примеры СУБД на этой модели:**
- **Hadoop + Hive** (SQL-подобный запросы поверх HDFS)
- **Apache Spark SQL** (быстрее, работает в памяти)
- **Greenplum** (кластерная PostgreSQL для аналитики)

**Если нужны не пакетные вычисления, а потоковая обработка** (данные идут постоянно) – можно **Apache Flink** или **Kafka Streams**.

### Какой тип СУБД выбрать?

| Если задача | Тип СУБД | Почему |
|-------------|----------|--------|
| Огромные объёмы + сложная аналитика (OLAP) | **Кластерная аналитическая (MPP)** – Greenplum, ClickHouse | Считают быстрее на 1000 машинах |
| Нужны быстрые точечные запросы и обновления (OLTP) | **NewSQL с шардированием** – CockroachDB, TiDB | Поддерживают ACID на тысячах узлов |
| Больше «перемалывания» данных (ETL, агрегации) | **MapReduce / Spark SQL** (на HDFS) | Проверенная модель, легко масштабируется |
```
